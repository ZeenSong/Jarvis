# M3.11：M3.1 修复后复验与 Jarvis 系统状态

复验日期：2026-09-16（Asia/Shanghai，约 22:40–23:05）。这是对 M3.1 的再次检查，不代表新增里程碑已验收。依据：[M3.1 架构基线](../Jarvis_M3.1_Architecture_Upgrade.md)及[上一轮清单](M3.1验收问题清单.md)。

## 1. 结论

**Jarvis 当前可运行，Luna 的多项修复有效；但 M3.1 Release Gate 仍不通过，而且阻塞项不只是实体 Android 验证。**

- 基础服务健康；服务端 52 项测试、Web 6 项回归、两套类型检查及 Web 构建通过。
- 已确认修复：生产 Hermes 可以回复并读取真实状态；新建 Workspace 不再白屏；同一 Artifact 可以更新；新 Workspace 不再带入旧源码；Web Markdown 基础语法；Session 撤销会关闭既有 WebSocket。
- 两项安全阻塞：**WebSocket 跨用户泄露私有事件；已批准的 Node 请求可以替换参数并重复执行。**
- 产品闭环仍有缺口：真实图表调用失败且工具状态不收敛；Core 没有创建任务/委派 Ops 的 MCP 工具；Web 热重连不触发 Refresh；空模型响应仍被标成成功。
- Android 已有 Markdown 渲染，但深色主题可读性和切换服务器后的状态清理仍有问题；实体机 Release Gate 本轮未验证。

不应继续把旧清单中的 G2/G5、F6、A5/A6/B3 等笼统标成“通过”。本报告不否定旧测试曾成功，只收窄其能证明的范围。

补充风险：

1. Node 容器使用 host network，默认 root，根文件系统可写；虽然 `privileged=false`，项目是只读挂载，但挂载整个项目和 `.codex` 目录。只读不等于不可读取凭据；应缩小挂载面。本轮没有读取这些凭据，也没有测试主机逃逸。

3. 留存测试库 `jarvis-android-postgres-final` 发布到 `0.0.0.0:5436`。建议确认用途并限制监听/认证；本轮未改动或关闭它。
4. 未发现 K8s CronJob 或匹配的 systemd 备份 timer；不能据此断言外部备份不存在，但异地备份及全量恢复验收尚无证据。`.local/m2-last-backup` 仍指向 9 月 12 日记录。
5. `agent.definition.list` 仍将 Core 标为 `runtime_type=deepseek`，实际主链路已用 Hermes；属于元数据迁移不一致，不应误判仍在使用旧手写 Core loop。

## 5. 当前缺陷与具体建议

### R01 · P0 · 私有 WebSocket 事件向其他用户广播

隔离环境创建不同用户 A/B。B 读取 A 的 conversation 返回 404，schedule.list 为空；但 B 的已认证 WS 收到 A 的 `schedule.created`（含私有 prompt）与 `conversation.message.delta`（含正文）。[原始记录](evidence/m3.11-20260916/isolated-results.json)的 `crossUser` 可复核。

原因：`apps/server/src/app.ts` 的 `push`（约 78 行）仅检查订阅 topic 和连接状态，没有逐连接 owner/resource 授权。HTTP 的 owner 过滤不能保护推送。

建议：事件携带内部可判定的 audience/owner；Server 在发送前鉴权，默认拒绝。审查 conversation、tool arguments/results、task/run、schedule、workspace、approval 全部事件，以及 legacy 未绑定用户设备。加入双用户同时在线测试，断言 HTTP 与 WS 一致。不要用客户端隐藏消息代替服务器隔离。

### R02 · P0 · Node 审批未绑定实际执行内容，可换参和重放

先批准 `node.codex.execute` 的 `APPROVED_INPUT_A`，再携带同一 approval_id 调用 `UNAPPROVED_DIFFERENT_INPUT_B`，两次均 HTTP 200，Mock Node 都收到 B。没有真实运行 Codex、没有执行危险命令。[证据](evidence/m3.11-20260916/isolated-results.json)的 `approval`。

`apps/server/src/m2.ts:455` 只匹配审批 ID、owner、status、capability，没有匹配 node_id、规范化 input，也未消费审批。此前“无审批/拒绝审批返回 403”的测试不足以证明完整边界。

建议：审批绑定 actor、node、capability、规范化参数 hash、有效期和执行幂等键；事务中原子消费，重放返回同一执行结果或拒绝，不再次派发。补换参、换节点、过期、并发双用及断线重试负测。

### R03 · P1 · 生产图表工具失败，状态卡不收敛

真实用户要求读取状态并展示图表。状态读取成功，但 `ui_view_show` 连续五次错误；模型报告 HTTP 400，页面最终“已完成”，五张工具状态仍是“运行中”，没有 Workspace 卡。[截图](evidence/m3.11-20260916/05-live-conversation.png)、[事件记录](evidence/m3.11-20260916/live-ui.json)。

MCP 的 intent/resources 仅为宽泛 string/list，缺少可发现的合法 schema/例子；具体 400 校验字段本轮未定位。Server 发 started 后，异常分支没有对应的 failed 终态。建议公开合法 enum/schema 与资源发现，错误返回结构化校验详情，并保证每个 started 最终 completed/failed/cancelled。

另有代码风险：`ui_view_show` 创建 native workspace，但未同时存储 native Artifact 或 Workspace→View 绑定；不能仅保存消息上的 workspace_id 就认为独立 Workspace 可恢复。修复后需真正从消息进入、刷新和另设备重开验收。

### R04 · P1 · Core 无法触发 Ops 持久任务/Node 执行

真实请求“委派 Ops，创建可追踪的只读 CPU 分析任务”，模型明确答复未创建，没有 Run ID。[截图](evidence/m3.11-20260916/08-live-delegation.png)。源码 `apps/hermes-mcp/jarvis_provider.py` 只暴露 system_status_read、system_metrics_read、agent_list、llm_usage_read、agent_run_status、ui_view_show。

直接通过 Kernel API 创建 Ops Run 的历史成功证据，不代表用户对话能抵达这条链路。建议补受授权控制的持久任务创建/查询/取消入口，返回稳定 task_id/run_id；经审批后才开放 Node 执行入口。保留 Hermes 负责推理、Kernel 负责权限/持久化的边界，不重新造手写 loop。

### R05 · P1 · Access 失效后的 Web 热重连仍掉线

保留 Refresh Cookie，仅移除 Access Cookie 模拟失效，并关闭实际浏览器 WS。等待约 6.5 秒，未出现 refresh 请求，auth/me=401，UI“重新连接”；刷新页面则 refresh=200、auth/me=200。[掉线截图](evidence/m3.11-20260916/14-web-expired-reconnect.png)、[刷新恢复](evidence/m3.11-20260916/15-web-refresh-after-reload.png)。

Cookie 截断错误已修复，但 reconnect 与初始挂载的恢复逻辑没有统一。建议实现共享 single-flight refresh，区分失效与主动撤销，避免 401 无限重连；测试后台休眠、断网恢复、Server 重连和多标签页。

### R06 · P1 · 空模型输出仍被记为成功

独立故障注入：模型返回空 SSE delta 后 DONE，Jarvis 持久化 `content=""`、`status="completed"`，没有 view/workspace/run。[原始结果](evidence/m3.11-20260916/empty-provider.json)。这不是说当前生产模型仍持续空回复，而是 Q01 的防护子问题尚未修复。

`packages/hermes-bridge/src/index.ts` 未拒绝空内容；`packages/conversation/src/index.ts` 只检查未处理 calls，然后 completed。建议对“没有正文且没有有效结构化结果”的完成做语义校验，保存可理解的失败原因，允许显式重试，不静默重放写操作。

### R07 · P2 · Android 视觉/跨服务器状态与应用跳转待完善

[实际 Markdown 截图](evidence/m3.11-20260916/24-android-markdown.png)证明语法已渲染，但深色背景上标题、正文和列表为黑字；引用/表格的颜色正常。切换到隔离服务器后，初次进入 Jarvis 曾显示旧服务器的消息；重新选会话后样本正确，顶部仍残留 `not_found`。这是客户端状态清理问题的可见证据，不据此断言 Server 跨用户返回旧内容。

建议统一正文主题色；登录/退出/换服务器时清除选中 conversation/workspace、消息缓存、连接和错误状态。应用跳转本轮 `appOpened=null`，尚未定位原因；检查 resolver 后异步 window.open 的弹窗限制，并在真实存在的资源上验证浏览器 fallback 与 Android Intent。

## 6. 建议执行计划与退出标准

| 顺序 | 工作包 | 必须满足的验收条件 |
| --- | --- | --- |
| 0 | 暂缓 M3.1 发布及新增用户/高风险能力开放 | 明确这是建议，本轮未停服务或改权限；先修 R01/R02 |
| 1 | 安全边界：事件授权 + 审批绑定 | 双用户所有私有事件零泄露；换参/换节点/过期/并发重放不能执行；正常合法执行仍可成功 |
| 2 | 身份可靠性与错误终态 | 热重连自动 Refresh；撤销连接不能复活；空输出 failed；每个工具 started 必有终态 |
| 3 | Hermes→Kernel 业务闭环 | 一次真实对话完成状态读取、图表生成、Workspace 重开；另一次创建 Ops Task，在任务列表看到稳定 ID/事件/结果 |
| 4 | 双端 UX / App Bridge | 深浅主题无黑字；切换账号/服务器无旧数据；Web 和实体 Android 打开真实 App 资源；取消/返回正常 |
| 5 | 发布与运维收尾 | 固定镜像 digest、源码与包 hash；修正 Core runtime 元数据；限制测试端口/挂载；设置 Hermes 资源预算；异地备份并恢复全部 M3.1 数据 |
| 6 | 完整 Release Gate | 同一候选版本重新跑自动测试、生产只读流程、安全负测、实体 Android 重启/覆盖更新/令牌续期；逐项附证据后再决定发布 |

不将完整 React worker、所有 Workspace 类型、所有 MCP/Skill、所有家庭共享 UI 等 M3.1 非目标扩大成阻塞范围。优先补齐现有最小闭环，而非继续增加页面和能力数量。
