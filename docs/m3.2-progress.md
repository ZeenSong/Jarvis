## 当前运行时验收证据

- Hermes profile `jarvis` 保留原生 Skills/toolsets，并同时发现 Jarvis MCP 的 14 个工具。
- 独立子智能体使用真实 Chrome/Playwright 重走了登录入口、消息发送、刷新/重新打开会话和“设置与待处理”路径；用户消息、Jarvis 回复、家庭服务空状态均可见。其验收临时会话已清理。
- 当前 r9 连续 15 次、间隔 1 秒的 `/health/live` 探测全部返回 200，最高延迟约 2 秒。部署仍是单副本 `Recreate`，发布新镜像时会有短暂不可用窗口；这是当前运维缺口，不能把“发布期间无中断”宣称为已完成。
- 自然语言联调曾触发不相关的安全扫描审批；该运行已安全停止且未批准命令。这个现象
  记录为 Hermes 原生能力验证结论，不改变用户要求的原生 Skills/MCP 优先架构。
- 第二次联调验证了 bridge 地址；由于 hostNetwork Pod 无法解析 Service 名称，改用
  `jarvis-server` Service 的 ClusterIP，并通过 profile `.env` 注入 `JARVIS_INTERNAL_URL`
  与 `JARVIS_BRIDGE_KEY`，不把 bridge secret 写入 ConfigMap。
- 服务器现在拒绝没有未来 `next_run_at` 的 `schedule_create`，要求先确认具体时间和时区；
  防止把“每天早上”错误地安排为一分钟后执行。真实 Chrome 已用明确的未来时间完成一次自然语言
  定时任务创建，并核对了数据库中的 `next_run_at` 与时区换算；验收测试任务已删除。

- r11/r12 现场回归暴露了一个真实稳定性问题：`system_overview` 的历史图把完整网络接口信息重复放进约 2712 个采样，单次 `view.v2.get` 响应约 39.6 MB，重复刷新会令 Node 堆达到上限并 OOM。r13 已将历史指标裁剪为 CPU/GPU/内存/磁盘字段；同一请求降至约 2.42 MB，4 个并发请求后 Pod 保持 `RESTARTS=0`。同时将 Web 错误回调稳定化，避免设置面板在登录绑定竞态下无限重试。
