# M2 双端上线验收

以下步骤应在生产升级后执行并记录，不能以本地测试代替。

1. 先核对旧 Android 配对仍有效，服务器、网络、GPU 与历史 AI 用量正常；记录生产镜像与数据库备份验证文件。
2. 在 Web 使用单独配对码连接，发送“你好，我叫小明，请记住”。在 Android 打开同一会话，询问名字，确认历史共享与流式回复。
3. 发送“CPU 现在多少？”，确认直接返回真实状态和动态图表，没有创建 Run。历史缺口必须可见。
4. 发送“请分析最近指标的变化原因，历史缺失请说明”，确认 Core 委派 Ops；展开父子 Run、五类只读工具、Timeline、真实 Token 与归档结果。
5. 发送“小型隔离验证：读取 package.json，新增 docs/m2-worker-smoke.md，写入隔离 Worker 验证，执行 Node 文件内容断言；不要提交或部署”。确认只使用配置的 `gpt-5.6-luna`，显示真实工具退出码、Diff、新增文件与用量。
6. 在另一端打开同一个 Run。刷新 Web、重建 Android 页面，切断再恢复网络，确认任务状态、消息与 revision 不倒退、不重复。
7. 在等待输入的测试任务提交补充内容；取消一个仍在运行的任务，确认活动子 Run 同时取消，晚到结果只归档、不改终态。审批不能提升隔离权限。
8. 检查 Worker 无主机挂载、Docker socket、生产凭据或 Kubernetes token；实测不能连生产数据库、Tailnet、Kubernetes API，出口只通过允许的模型/依赖代理。
9. 验证正常归档后 Job 销毁、工作卷保留；在独立集群重启 Gateway，确认未完成任务明确失败、日志恢复与清理，不重做副作用。
10. 核对数据与旧设备，执行一次独立环境镜像回退，记录通过与未通过项，再发布 v0.2.0。

当前本地证据见 [验收记录](acceptance.md)。真实 Codex、Ops 委派已通过；双端输入与取消目前使用自动化测试 Runtime，实际 Kubernetes 故障注入仍未执行。
