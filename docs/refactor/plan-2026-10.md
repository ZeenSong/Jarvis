# Jarvis 系统重构计划（2026-10）

> 分支：`refactor/systems-2026-10`
> 基线：`main@aca6dc0` + 线上 `jarvis-server:0.4.0-visual-refresh-20261017`
> 回滚：`.local/refactor-backup/jarvis-pre-refactor-*.dump` + `.local/refactor-backup/rollback-image.txt`

## 0. 原则

1. **不推倒重来。** 保留 Fastify + Postgres + zod + 现有协议，重构其上的隐含假设。已经在跑的家庭服务不能停。
2. **每个阶段必须可部署、可回滚、有验收。** 阶段之间不共享未完成的重构。
3. **单实例假设要么被移除，要么被断言。** 不允许"看起来能扩、扩了就坏"。
4. **接入新应用必须退化为配置。** 这是本轮的北极星指标：新增一个 Hermes 集成 = 一份 manifest + 一个凭据，0 行 TS 代码、0 处 switch。
5. **提示词不是权限边界。** 任何副作用必须由能力层强制。

## 1. 阶段与验收门禁

| 阶段 | 内容 | 验收门禁 |
| --- | --- | --- |
| **P0 安全网** | 分支、DB 快照、回滚镜像、CI 基线 | `npm test` 基线无回归 |
| **P1 地基** | 类型化错误与单一错误映射、版本单一来源、安全响应头、登录防爆破与恒定时间、结构化日志与请求 ID、版本化迁移 | 单测覆盖映射与限速；线上 `/health` 版本正确；无 500 泄漏 |
| **P2 执行模型** | DB 租约 + `SKIP LOCKED`、有界重试与死信、`recover` 语义重写、per-runtime 并发池、清理循环修复 | 3 个泄漏 instance 收敛；`run_events` 停止增长；杀进程后 30s 内恢复 |
| **P3 集成注册表** | 声明式 provider manifest（传输/凭据/工具策略/应用描述/图标/深链/scope），通用 MCP 网关，管理端 CRUD，迁移 HA+Immich 到 manifest | 新增第 3 个应用（Jellyfin 或 qBittorrent）**只改配置**即可出现在应用页并可被模型调用 |
| **P4 会话与流式** | 增量事件（只带 delta）、分块持久化 + 检查点、事件保留策略、`m2_idempotency` 分表与索引 | 长回复出网字节 O(n)；无 Seq Scan |
| **P5 协议与 UI** | v2-only、视图类型注册表（替代 4 个 preset）、导航/路由闭环、执行时间线状态机、系统页布局、结果/工作区真实使用率 | 每个页面可达且无 404；时间线不再卡"正在执行"；新增一种视图类型不改渲染代码 |
| **P6 安全与流程** | CSP/XFO/HSTS、OIDC 策略显式化、凭据密钥轮换、Hermes dashboard 单一身份、CI 全门禁（web build/test、Android instrumentation、lint、依赖扫描）、镜像 tag 规范化 | CI 全绿；部署可移植（无个人绝对路径） |
| **P7 上线** | 迁移 + 数据修复 + 灰度 + 实机验收 | 家庭场景回归 + Android 真机链路 |

## 2. 北极星：集成为什么必须变成配置

今天的接入成本（每个应用都要改）：

- `app.ts` 的工具 switch + scope 映射（约 40 行/应用）
- `m2.ts` 的 `capabilityCatalog` + `app.resolve` 分支 + `application.list` 数据源
- `applications.ts` 的应用清单与图标
- `hermes-integrations.ts` 的适配函数
- `jarvis_provider.py` 的 `_upstream()` 分支与专用工具
- `mcp-access.ts` 的 provider 联合类型
- 环境变量、图标资源、深链模板、测试

目标形态（`integrations/<id>/manifest.json`）：

```json
{
  "id": "jellyfin",
  "name": "Jellyfin",
  "kind": "mcp",
  "transport": { "type": "streamable-http", "endpoint_env": "JELLYFIN_MCP_URL" },
  "credential": { "env": "JELLYFIN_API_KEY", "header": "Authorization", "scheme": "Bearer" },
  "tools": { "read": ["*_search", "*_list", "*_get"], "write": ["*_create", "*_delete"], "deny": [] },
  "scopes": { "read": "jellyfin.read", "write": "jellyfin.write" },
  "app": { "icon": "jellyfin", "launch_env": "JELLYFIN_URL", "deep_links": { "item": "{base}/web/index.html#!/details?id={id}" } },
  "capabilities": ["media.read"]
}
```

服务端的 provider 解析、scope 派生、凭据读取、工具授权、应用卡片、深链全部由 manifest 驱动。新增应用 = 放一个目录 + 配一个环境变量。

## 3. 立即执行的缺陷修复（P0/P1，本轮）

- `recover(true)` 无终态重试 → 线上 121,432 条垃圾事件，仍在增长
- 登录无速率限制；用户名枚举实测 0.7ms vs 11ms
- HTML 无任何安全响应头
- `SERVER_VERSION` 硬编码 0.3.2，`/health` 与系统页均错
- `/agents` 路由 404；`系统`/`Hermes` 藏在 `?developer=1`
- 执行时间线卡在"正在执行"（1 条 `reasoning/running` 未收敛）
- 系统页 1440px 布局塌陷
- 两份重复的 error handler（`app.ts:811` / `:1126`）

## 4. 非目标（本轮明确不做）

- 多家庭（household 多租户）的产品化
- 移动端上架与推送通道（保留通知中心）
- 把模块化单体拆成微服务
- 重写 Android 客户端（只保持协议兼容并补关键缺陷）
